# ReconcileKit — Architecture

**Version:** 0.1  
**Status:** FROZEN  
**Scope:** MVP  
**Architecture basis:** CANONICAL-DOMAIN-MODEL-v0.3 + PAYSTACK-EVIDENCE-VALIDATION-v0.2

## 1. Purpose

This document defines the implementation architecture for the ReconcileKit MVP.

The architecture is derived from the frozen domain model and validated Paystack evidence.

It defines:

- system boundaries;
- dependency direction;
- package/module responsibilities;
- provider adapter boundaries;
- CLI boundaries;
- configuration boundaries;
- validation and testing boundaries;
- data flow;
- extension points;
- explicit architectural non-goals.

It does **not** freeze a persistence technology, hosted infrastructure, ORM, or SaaS architecture.

## 2. Architectural Principles

### 2.1 Domain first

The domain model is authoritative for reconciliation semantics.

Infrastructure and provider concerns must adapt to the domain rather than redefine it.

### 2.2 Provider neutrality

The core reconciliation engine must not know Paystack API structures, endpoints, status names, or currency quirks.

Provider-specific behavior belongs in adapters.

### 2.3 Determinism

Identical normalized inputs and configuration must produce identical reconciliation results.

No fuzzy, probabilistic, or heuristic matching exists in MVP.

### 2.4 Dependency inversion

Dependencies point inward toward stable domain concepts.

```text
CLI / adapters / infrastructure
            ↓
      application layer
            ↓
       domain layer
```

The domain must not depend on the CLI, Paystack, filesystem, database, or network.

### 2.5 Local-first MVP

The first implementation is a local CLI/package.

Hosted infrastructure is explicitly deferred.

### 2.6 Open-source core

The core reconciliation engine must remain independently usable as a package/library.

The CLI is a consumer of the core, not the owner of its business logic.

## 4. Layer Model

### 4.1 Domain

The domain contains provider-neutral business semantics.

Responsibilities:

- canonical payment representations;
- exact-reference matching;
- duplicate detection;
- validation;
- discrepancy collection;
- outcome classification;
- reconciliation report semantics.

The domain must not import:

- Paystack SDKs;
- HTTP clients;
- CLI frameworks;
- filesystem libraries;
- database clients;
- Prisma;
- PostgreSQL-specific code.

### 4.2 Application

The application layer orchestrates use cases.

Responsibilities:

- coordinate ingestion;
- invoke adapters;
- coordinate normalization;
- invoke reconciliation;
- collect results;
- coordinate output.

The application layer may depend on domain abstractions.

It must not embed provider-specific reconciliation rules.

### 4.3 Adapters

Adapters translate external representations into domain representations.

Initial adapters:

```text
Merchant CSV adapter
Merchant JSON adapter
Paystack transaction adapter
```

Responsibilities:

- parse source data;
- validate source shape;
- map source fields;
- map provider statuses;
- map provider currencies/amounts;
- preserve source attributes;
- expose provider-neutral records.

### 4.4 CLI

The CLI is an interface adapter.

Responsibilities:

- parse command-line arguments;
- load configuration;
- select input adapters;
- invoke application use cases;
- render human-readable output;
- emit machine-readable output;
- return appropriate process exit status.

The CLI must not implement reconciliation rules.

## 7. Matching Architecture

MVP matching is exact-reference only.

```text
MerchantPayment.merchant_reference
                 │
                 ▼
       exact-reference index
                 │
                 ▼
ProviderPayment.reference
```

Algorithm:

```text
1. Validate source records
2. Detect duplicate identities
3. Detect missing/unusable references
4. Build reference indexes
5. Determine correspondence
6. Run applicable validations
7. Collect all codes
8. Produce MatchResult
```

The implementation must never select an arbitrary candidate from a duplicate set.

## 8. Duplicate Detection Architecture

Duplicate detection happens before ordinary one-to-one comparison.

Conceptual indexes:

```text
merchant_reference → MerchantPayment[]
provider_reference → ProviderPayment[]
```

Cardinality determines the matching state:

```text
0 provider candidates
    → MISSING_PROVIDER_RECORD

1 provider candidate
    → normal comparison

>1 provider candidates
    → DUPLICATE_PROVIDER_RECORD
       + counterpart HELD_AMBIGUOUS
```

Equivalent logic applies to duplicate merchant records:

```text
>1 merchant candidates
    → DUPLICATE_MERCHANT_RECORD
       + counterpart HELD_AMBIGUOUS
```

Code vocabulary:

- `DUPLICATE_MERCHANT_RECORD` / `DUPLICATE_PROVIDER_RECORD` identify the duplicated reference set on the affected side.
- `CONFLICTING_ATTRIBUTES` is a detail code attached to a duplicate set whose records carry materially conflicting attribute values; it does not replace the duplicate code.
- `HELD_AMBIGUOUS` describes the unsafe single-counterpart disposition: the counterpart is not arbitrarily paired and is not misclassified as missing/unmatched.
- No record is ever arbitrarily selected from a duplicate set.

## 9. Validation Architecture

Validation is modular.

Conceptual validators:

```text
AmountValidator
CurrencyValidator
StatusValidator
TimestampValidator
```

The `CurrencyValidator` compares currencies; it does not decide whether a currency is supported:

- input/source validation determines whether a currency is valid and supported for the configured input/provider boundary;
- invalid or unsupported currency produces `INPUT_ERROR` before normal reconciliation and never enters domain comparison;
- domain currency comparison operates only on valid, comparable currencies;
- valid currencies that differ produce `CURRENCY_MISMATCH`.

A validator returns structured validation information rather than directly deciding the entire reconciliation outcome.

Example:

```text
ValidationResult
  applicable
  passed
  code
  note
```

The reconciliation engine aggregates results.

It does not use first-failure semantics.

```text
validators
   ↓
[pass, amount mismatch, status unresolved, ...]
   ↓
classification
   ↓
MatchResult
```

## 10. Outcome Classification

Classification is centralized in the domain.

Input errors occur before normal reconciliation.

For valid records:

```text
unique correspondence
        ↓
run applicable validators
        ↓
confirmed discrepancy?
   ┌────┴────┐
  yes       no
   ↓         ↓
DISCREPANCY  unresolved validation?
             ┌────┴────┐
            yes       no
             ↓         ↓
        UNRESOLVED    MATCH
```

Duplicate/ambiguity states are handled before ordinary validation:

```text
duplicate candidates
       ↓
HELD_AMBIGUOUS
```

## 11. Status Mapping Architecture

Paystack status mapping belongs entirely inside the Paystack adapter.

Conceptually:

```text
Paystack raw status
       ↓
PaystackStatusMapper
       ↓
CanonicalPaymentStatus
       +
SourceAttributes.original_status
```

Current mapping:

```text
success    → SUCCESS
failed     → FAILED
pending    → PENDING
processing → PENDING
ongoing    → PENDING
queued     → PENDING
abandoned  → UNKNOWN
reversed   → UNKNOWN
```

`abandoned` and `reversed` must not be mapped to `CANCELLED` without a future domain decision.

## 12. Paystack Adapter Boundary

The Paystack adapter owns:

- Paystack API interaction;
- request/response transport;
- extraction of `data.reference`;
- extraction of `data.amount`;
- extraction of `data.currency`;
- extraction of `data.status`;
- status normalization;
- currency/subunit normalization;
- timestamp-field selection;
- preservation of source attributes;
- provider-specific error handling.

The core must never inspect a raw Paystack response.

Conceptually:

```text
Paystack API
     ↓
PaystackAdapter
     ↓
ProviderPayment
     ↓
Application
     ↓
Domain
```

## 13. Paystack API Status Safety

The adapter must explicitly distinguish:

```text
response.status
```

from:

```text
response.data.status
```

The transaction status comes from the transaction data object.

This rule must be covered by an adapter test.

## 14. Currency and Amount Boundary

The Paystack adapter owns provider-specific currency/subunit behavior.

Flow:

```text
Paystack amount + currency
          ↓
currency/subunit validation
          ↓
integer canonical amount
          +
canonical CurrencyCode
```

The domain receives only the normalized representation.

No Paystack-specific XOF/subunit logic belongs in the domain.

## 15. Timestamp Architecture

Timestamp validation is configurable.

The adapter selects the provider timestamp mapped to:

```text
ProviderPayment.occurred_at
```

The architecture must not hard-code a universal Paystack timestamp field or tolerance.

Configuration concept:

```text
timestamp_validation:
  enabled: boolean
  tolerance: duration
```

If timestamp validation is enabled but required timestamps are unavailable, the validation is unavailable rather than failed.

The final Paystack timestamp-field choice must be validated against representative provider test transactions before implementation.

## 17. Output Architecture

The domain produces structured results.

Output adapters transform them into:

```text
Human-readable CLI
Machine-readable JSON
```

CSV/JSON are the initial input formats.

The output layer must not alter domain classifications.

Non-exhaustive example conceptual output:

```text
summary:
  total
  matched
  discrepancies
  unresolved
  held_ambiguous
  input_errors

results:
  ...
```

The summary vocabulary must remain capable of representing missing provider records, unmatched provider records, and counts by discrepancy code in addition to the fields shown above. This example is not a serialization specification.

## 18. Configuration

Configuration belongs outside the domain.

Initial configurable concerns include:

```text
timestamp validation enabled/disabled
timestamp tolerance
input format
output format
provider selection
```

Configuration should be resolved by the application/CLI layer and passed into domain operations as explicit values.

The domain must not read environment variables directly.

## 19. Error Architecture

Errors should be separated into:

### Domain reconciliation outcomes

The unified top-level outcome vocabulary includes the reconciliation states:

```text
MATCH
DISCREPANCY
UNRESOLVED
HELD_AMBIGUOUS
MISSING_PROVIDER_RECORD
UNMATCHED_PROVIDER_RECORD
MISSING_REFERENCE
INPUT_ERROR
```

`INPUT_ERROR` is a domain reconciliation outcome: it represents a record that cannot enter reconciliation as valid canonical input. It is not an operational exception.

Input errors occur before normal reconciliation and are not classified as reconciliation discrepancies.

### Operational / infrastructure failures

Operational failures such as:

```text
network failure
provider API failure
file read failure
malformed external response
```

Operational failures are not domain reconciliation outcomes. They must not be silently converted into reconciliation discrepancies.

## 20. Explainability

Every reconciliation result must be explainable from:

```text
source inputs
normalized values
configuration
validation results
classification rules
```

The system should preserve:

- merchant identifiers;
- provider identifiers;
- original source status;
- relevant source timestamps;
- discrepancy codes;
- validation notes.

This is especially important for an open-source reconciliation tool intended for investigation rather than opaque scoring.

## 23. Ports

Where external interaction is required, the application layer should define interfaces/ports.

Ports are for replaceable external systems. Examples:

```text
MerchantRecordSource
ProviderTransactionSource
ReportWriter
```

The exact interface names are implementation decisions.

Application-to-domain calls, including invoking the reconciliation service, do not require a port: the application depends directly on the domain service. Orchestration of reconciliation remains an application responsibility.

The architectural principle is:

> External systems are replaceable implementations behind stable application boundaries.

## 24. Persistence

Persistence is **not part of the MVP architecture contract**.

The MVP should operate on in-memory domain representations.

Do not introduce:

- PostgreSQL
- Prisma
- Redis
- database migrations
- ORM entities

unless a concrete requirement later establishes the need.

If persistence is introduced later, it must sit outside the domain and application semantics.

## 25. HTTP / Network Boundary

Network access is limited to provider adapters in the MVP.

The domain and application reconciliation logic must not perform HTTP requests directly.

Conceptually:

```text
Application
    ↓
Provider Port
    ↓
Paystack Adapter
    ↓
HTTP
    ↓
Paystack
```

## 26. Security and Secrets

Provider credentials belong outside the domain.

The Paystack adapter may receive credentials through application configuration.

Secrets must not be:

- stored in domain objects;
- logged;
- embedded in source code;
- included in reconciliation reports.

Environment/configuration handling is an infrastructure concern.

## 27. Observability

MVP logging should support diagnosis without exposing secrets.

Logs may include:

- operation type;
- provider;
- record counts;
- duration;
- result counts;
- non-sensitive identifiers where appropriate.

Logs must not expose:

- secret keys;
- authorization headers;
- sensitive payment credentials.

Exact logging framework selection is deferred.

## 28. Performance Boundary

The MVP architecture should support deterministic in-memory reconciliation.

The reference indexes should allow approximately:

```text
O(n + m)
```

matching/index construction for `n` merchant records and `m` provider records, excluding input parsing and validation costs.

The architecture should not require nested comparison of every merchant record against every provider record.

Large-scale distributed processing is deferred.

## 29. Extension Model

Future provider adapters should implement the same provider-neutral boundary:

```text
ProviderAdapter
      ↓
ProviderPayment
```

Potential future adapters:

```text
Stripe
Flutterwave
PayPal
other payment providers
```

These are examples of extension points, not MVP commitments.

A new provider must not require changes to the core matching algorithm merely because its raw API differs.

If a provider introduces genuinely different reconciliation semantics, that difference must be surfaced as a domain decision rather than hidden inside an adapter.

## 30. Architecture Decision: CLI Package

The open-source CLI is the first delivery surface.

Conceptually:

```text
reconcilekit <command> [options]
```

The CLI should be thin.

It must:

- parse arguments;
- resolve configuration;
- invoke application services;
- render results;
- set process exit status.

It must not own matching logic.

## 31. Architecture Decision: Package Reusability

The reconciliation engine must be usable independently of the CLI.

Target conceptual usage:

```text
library consumer
      ↓
application/domain API
      ↓
reconciliation engine
```

This allows future:

- dashboards;
- hosted services;
- automation;
- CI integrations;
- internal tooling;

without rewriting the core.

## 32. Architecture Decision: No Premature Enterprise Infrastructure

The full enterprise direction may eventually include:

```text

database
```

None of these are required for the MVP.

The architecture must leave clean extension boundaries without implementing them prematurely.

## 33. Architecture Risks

### Risk 1 — Provider semantics leaking into domain

Mitigation:

Strict adapter mapping and provider-neutral domain types.

### Risk 2 — First-failure validation

Mitigation:

Validation aggregation and explicit discrepancy-code collection.

### Risk 3 — Duplicate arbitrary pairing

Mitigation:

Duplicate detection before candidate selection.

### Risk 4 — Timestamp assumptions

Mitigation:

Configurable timestamp validation and no frozen provider default.

### Risk 5 — Status semantic collapse

Mitigation:

Preserve source status and keep uncertain mappings as `UNKNOWN`.

### Risk 6 — Infrastructure premature adoption

Mitigation:

Persistence and enterprise infrastructure explicitly deferred.

## 38. Authorized Decision: Live Paystack CLI Contract

**Status: AUTHORIZED (product/CLI contract record — no implementation).**

This section records the live-Paystack product/CLI contract authorized for the client-facing MVP. It extends, and does not modify, the decisions above.

### 38.1 Live requirement

Live Paystack transaction fetching is IN SCOPE for the client-facing MVP, invoked only through an explicit opt-in (see 38.2). The existing file-based `--provider <path>` mode remains supported and behaviorally unchanged.

### 38.2 CLI mode contract

- `--merchant <path>` — required merchant CSV input (unchanged).
- `--provider <path>` — existing file-based provider mode (unchanged).
- `--live-paystack` — explicit live Paystack provider mode (new).

Rules:

- `--provider` and `--live-paystack` are mutually exclusive.
- `--live-paystack` explicitly opts into network access.
- Absence of `--provider` must never silently trigger network access.
- Merchant input remains required.
- No subcommand is introduced; the CLI is not redesigned beyond this explicit live mode.

### 38.3 Secret boundary

- The live CLI reads the Paystack secret from the environment variable `RECONCILEKIT_PAYSTACK_SECRET_KEY`.
- The CLI passes the secret through explicit application/transport configuration.
- The Domain, Application, and transport must not read `process.env`.
- No secret-management dependency is added.
- The secret is not accepted as a CLI argument, not read from a file, and not hard-coded.
- The secret must never be printed, logged, serialized, or included in errors or reconciliation reports.

### 38.4 Missing-secret semantics

When `--live-paystack` is selected and `RECONCILEKIT_PAYSTACK_SECRET_KEY` is absent or empty:

- classify as an input/configuration failure;
- return CLI exit code `1`;
- emit a deterministic user-facing error stating that the Paystack secret is required for live mode;
- never expose the secret value.

### 38.5 Transport-control policy

No new CLI controls are introduced for timeout, retry count, retry/backoff, rate-limit waiting, pagination, or base URL. The transport's existing internal behavior is reused; no such policies are invented.

### 38.6 Authorized live path

```text
CLI
  → fetchPaystackTransactions()
  → mapPaystackResponses()
  → ProviderPayment + SourceAttributes
  → reconcileRecords()
  → reconcile()
  → CLI output
```

The CLI must not perform Paystack mapping or reconciliation logic. The Application remains provider-neutral. The Domain remains HTTP-independent.

### 38.7 Authorization boundary

This section authorizes the contract only. It does not wire the CLI, modify `src/`, change `package.json`/`package-lock.json`, add dependencies or environment files, change existing file-mode exit-code behavior, or change the transport implementation. Implementation proceeds only under a separate implementation gate.
