# Contact Enrichment Log — Column & Cache Contract

Contact Enrichment V1 requires a new **Contact Enrichment Log** tab in the
production sheet (decision D-C0). This tab is the durable, sheet-backed cache
for all contact lookups. It is created once by the operator; the n8n workflow
never reads or writes any other tab's enrichment data.

## Columns (A–N, in order)

| Col | Column               | Type     | Semantics                                                                          |
| --- | -------------------- | -------- | ---------------------------------------------------------------------------------- |
| A   | `enrichment_id`      | text     | Deterministic `ENRICH-<fnv1a32-8hex>` of `enrichment_key::enriched_at`              |
| B   | `enrichment_key`     | text     | `domain::provider` — the cache key (one row per key per provider)                  |
| C   | `lead_id`            | text     | Source lead id from Raw Leads / Approved Outreach                                  |
| D   | `provider`           | text     | `hunter` \| `oss` \| `manual`                                                      |
| E   | `query_input`        | text     | Domain queried (lowercase, protocol/path stripped)                                 |
| F   | `result_email`       | text     | Best email returned (empty when none)                                              |
| G   | `result_contact_name`| text     | Best-match contact name (empty when none)                                          |
| H   | `result_contact_title`| text    | Best-match contact title (empty when none)                                         |
| I   | `result_verified`    | bool     | `TRUE`/`FALSE` — Hunter's own verification for accepted emails; manual rows `FALSE` unless operator-verified |
| J   | `credits_consumed`   | integer  | Credits charged by the provider (empty = 0)                                        |
| K   | `enriched_at`        | datetime | ISO-8601 timestamp of the enrichment                                               |
| L   | `ttl_expires_at`     | datetime | `enriched_at` + 60 days (cache validity window)                                    |
| M   | `cache_hit_count`    | integer  | How many times this key was served from cache (write-back on each hit)             |
| N   | `notes`              | text     | OSS fallback / manual placeholder decisions                                        |

Booleans on the sheet use the repo's `TRUE`/`FALSE` string convention
(precedent: `has_website` / `has_phone` on Verified Leads).

## Cache semantics

- **Keyed by `enrichment_key` only** (`domain::provider`), not by lead: the same
  domain returns the same enrichment within a run and across runs.
- A **hit** is a row whose `ttl_expires_at` is strictly after the run timestamp;
  a hit means the provider is never called and `cache_hit_count` is incremented
  (write-back).
- A **miss** (no row, or row expired past TTL) triggers the provider call; the
  new row is appended via `upsertCache` (replace-by-key), never duplicated.
- Referential semantics are **read-first per run**: the node always re-reads the
  tab, so an operator can prune/expire rows between runs and the engine honors it.
- Determinism: log rows sort by `(enrichment_key, enriched_at, lead_id)`
  ascending; `enrichment_id` and `ttl_expires_at` are pure functions of content
  (no `Date.now()`/`Math.random()`).

## Providers

| Provider | Meaning                                                                                      |
| -------- | -------------------------------------------------------------------------------------------- |
| hunter   | Hunter.io `domain-search` (paid credits; see `docs/OVERTURE-LOADER.md` for the business half) |
| oss      | Zero-credit fallback pipeline (`@absolutejs/enrich` → coldreach → manual placeholder)        |
| manual   | Operator-decided placeholder (systems where no contact exists)                                |

Only `hunter` rows may consume credits. The `oss`/`manual` rows carry `notes`
explaining the decision so a later operator can revisit.

## New columns on existing tabs

See `docs/HANDOFF-SPEC.md` for the handoff-visible changes. Enrichment adds:

- **Verified Leads (Raw Leads):** `enrichment_business_status`,
  `enrichment_confidence`, `enrichment_gers_id`, `enrichment_last_run`.
- **Approved Outreach:** `contact_blocked`, `contact_source_provider`.

`contact_source_provider` records which provider produced the accepted email
(`hunter`/`oss`) or `manual` when an operator placed a decision; `contact_blocked`
marks leads that must never be auto-added to an outreach run.

# Phase 6.6 — Enrichment V1 workflow artifact lock

The H.6 envelope is delivered as a **deterministic 16-node n8n workflow**
(`Enrichment V1.json`, generated by `scripts/build-enrichment-workflow.js`,
rebuild byte-identical via `npm run enrichment:build`). It reads the Approved
Outreach + Contact Enrichment Log tabs, enriches through Hunter, falls back to
the zero-credit OSS pipeline, consolidates, and writes back only the two
enrichment-owned columns on Approved Outreach plus append rows on the log tab.

## Topology (canonical order, x-step 260)

1. `Manual Trigger` → 2. Read Log → 3. Read Approved → 4. Prepare Enrichment
   Scope → 5. Enrich Contact (embedded mirror) → 6. Prepare OSS Fallback Scope →
   7. Enrich Contact OSS Fallback (embedded mirror) → 8. Consolidate →
   9. `Has Enrichment Output?` IF → branches to [10 Split Log / 12 Split
   Updates] on true, 16 No-Op End on false; 10 → 11 Write Log (append, leaf);
   12 → 13 Update Approved (match on `lead_id`, 7 owned columns) → 14 Report →
   15 Enrichment Complete (leaf).

## Behavioral contract

- **Clean-source nodes only.** All 8 code nodes pass `assertCleanSource`
  (no `require`, `fetch`, `Math.random`, `Date.now`, `$env`, `process.env`,
  `new Function`, `eval`, `https://`). No Hunter credential, Authorization
  header, or hardcoded key ships in the artifact; `npm run enrichment:security`
  re-scan-certifies both shipped workflows.
- **`alwaysOutputData` on 6 nodes** (both Prepare nodes, both Enrich nodes,
  Consolidate, Report) so a 0-lead batch or a provider returning zero items never
  collapses the chain into the No-Op branch by accident.
- **Empty scope determinism is explicit:** `Prepare Enrichment Scope` returns
  `[]` with zero leads; `Prepare OSS Fallback Scope` returns `[]` on a fatal
  contact run or zero total; a fatal-only run converges to the **No-Op End** with
  zero updates and zero log rows (verified by fixture TEST-ENRICH-011).
- **Provider seam injection is the only non-deterministic boundary.** The runner
  injects `now/runId/run_timestamp/run_id/hunterResults/hunterFailures/ossResults`
  on the input of the Prepare nodes; every node consumes it from its input or an
  explicit `$('...')` reference. Any value injected must be deterministic within
  a run — the nodes never reach for wall-clock time.
- **Consolidation precedence (contact → OSS, first-wins with richer-row
  upgrade):** for a lead enriched by both providers the keep-rule is
  **strictly more non-empty owned fields** replaces a stub, so a Hunter
  `no_emails_found` stub (`provider: hunter`, empty email) never shadows an
  OSS-filled email or a manual block for the same lead; ties keep the earlier
  (Hunter) row.
- **Log append is cache-aware:** log rows merge by `enrichment_key`; rows whose
  key is already present in the tab (cache hits, including the write-back row
  with its incremented `cache_hit_count`) are filtered by Split Enrichment Log
  Rows so the append payload never duplicates a live cache row.
- **Report node** emits only run/provided metrics (`run_id`, `run_timestamp`,
  per-provider totals, `approved_updates`, `enrichment_log_rows`) and never raw
  lead fields.

## Parity & freeze evidence

- `tests/enrichment-workflow-build.test.js` (29 tests) pins: 16-node identity
  (ids/names/types/positions), canonical edges + terminals, ancestry of every
  `$('...')` reference, embedded byte-parity for the two mirror nodes, update/
  append/IF shape, clean-source on all code nodes, deterministic rebuild
  byte-match, and chain-vs-engine parity on contact fixtures TEST-ENRICH-007
  through 013 (including the OSS fallback, manual block, cache-hit, fatal, and
  empty-run paths). Full suite: 1108 tests green.
- The frozen-artifact manifest (`R-ENRICH-1`) pins the sha256 of every
  enrichment source, fixture, and the shipped workflow; `node
  scripts/verify-frozen.js` re-asserts the enrollment trend at each freeze.

# Phase H.8b — Engine-direct live runner

`scripts/run-enrichment-live.js` executes the SHIPPED contact-enrichment engines
(`src/enrichment-contact.js` + `src/enrichment-contact-oss.js`) engine-direct
against the production sheet — no workflow runner involved. It shares every code
path with the workflow only through those frozen engines and the shared column
contracts, so results stay byte-consistent with what the n8n build would do.

## Behaviour

- **Default mode is DRY_RUN**: read-only. Nothing is written without
  `--execute`, and there is deliberately no `--allow-production-writes`.
- **Namespace guard, always enforced on writes.** With `--execute`, log rows,
  cache-hit write-backs, and Approved Outreach V/W cells are written ONLY for
  `lead_id`s under `TEST-ENRICH-LIVE-<tag>` (`^TEST-ENRICH-LIVE-[0-9a-f]{8,32}-`).
  Non-namespaced production leads are enriched and reported as `would-append`
  /`would-update` but never written.
- **Approved Outreach writes are V/W only** (`contact_blocked` = V,
  `contact_source_provider` = W — the last two columns, owned by enrichment).
  Columns A–U are never written.
- **Log writes are append-only on A–N** plus `cache_hit_count` write-back on M.

## CLI

```
node scripts/run-enrichment-live.js [flags]     # or: npm run enrichment:run --
  --execute            allow namespaced writes (append log, bump M, update V/W)
  --limit=<N>          max eligible leads to enrich (default 5)
  --lead-ids=<id>,<id> restrict scope to these lead_ids
  --provider=<name>    agentdata | hunter (default ENRICHMENT_PROVIDER or agentdata)
  --namespace=<prefix> test namespace (default TEST-ENRICH-LIVE-<hex tag>)
  --reports-dir=<dir>  report output directory
  --no-interactive     never prompt
  --help
```

Env (see `.env.example`): `GOOGLE_SHEET_ID`, `GOOGLE_ACCESS_TOKEN` or
`GOOGLE_SERVICE_ACCOUNT_JSON`, `AGENTDATA_API_KEY` (default provider),
`HUNTER_API_KEY` (when `ENRICHMENT_PROVIDER=hunter`), `ENRICHMENT_PROVIDER`,
`ENRICHMENT_TTL_DAYS` (60), `ENRICHMENT_MIN_SCORE` (50).

Exit codes: **0 PASS, 1 FAIL, 3 NOT_CONFIGURED**.

## Preflight checks

`B config present` · `C sheet auth` · `D Approved Outreach columns` ·
`E Contact Enrichment Log columns` (exact-missing-column list on failure) ·
`F provider` · `G <provider key>` · `H namespace well-formed` (informational —
an adversarial namespace only refuses to execute). Any non-informational failure
aborts before any read/enrich/write.

## Phase H.8b.1 - Preflight observability fix

- Symptom: with GOOGLE_SHEET_ID / GOOGLE_ACCESS_TOKEN / AGENTDATA_API_KEY set
  and ENRICHMENT_PROVIDER=agentdata, the runner exited FAIL at preflight in
  <1ms with failure_info: ["preflight failed"] and no per-check detail.
- Root cause (runner defect): runEnrichment ran preflight BEFORE the Sheets
  surface was built (the client was created after the preflight FAIL branch).
  With no deps.client, check "D/E sheet reads" always pushed
  "no Sheets client available" -> hard FAIL -> exit before any network call.
  The environment being configured was irrelevant; the check could never pass
  in CLI mode.
- Fix:
  - The Sheets surface is now built BEFORE preflight (only when config is
    CONFIGURED) and handed to preflight via a deps clone {client, clientError};
    a client-construction failure is captured as clientError and surfaces as
    the "D/E sheet reads" detail instead of aborting.
  - Every preflight check is named and reported: report gains preflight_detail
    (array of {name, ok, informational, detail}) - the only new public field.
  - failure_info now carries the specific failing check, e.g.
    preflight failed: D/E sheet reads (ENOENT: ...).
  - Check "F provider" now names the offending value when invalid
    (provider "<value>" invalid; must be one of agentdata|hunter).
- Tests: 6 added (per-check shape, named FAIL for a bad provider, report
  failure_info naming the check, missing-column FAIL naming, PASS reports carry
  preflight_detail, client-construction failure named as D/E). Runner suite:
  52/52. Whole suite: 1194/1194.
- Gates: npm test 1194 pass; verify:frozen 24/24 PASS; enrichment:security
  exit 0 (GREEN).
- No workflow / schema / engine / manifest changes. No --execute.
