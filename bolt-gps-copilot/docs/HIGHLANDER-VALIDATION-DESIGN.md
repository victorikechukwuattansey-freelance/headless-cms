# HIGH-LANDER ECONOMIC VALIDATION — DESIGN v1

**Phase:** Bolt GPS Copilot — next phase: Highlander economic validation.
**Status:** DESIGN FOR REVIEW. Per directive §21, **no code was modified** (`index.html` untouched).
**Goal:** discover the 2005 Toyota Highlander's true sustainable NET_AFTER_FUEL on Bolt in Abuja, and measure the Copilot's incremental economic value — not to manufacture ₦300k/month.

---

## A. Proposed architecture

Target: keep the app a browser-based demo, but split it into two files so the economic core is unit-testable and reusable by both the UI and the paired-experiment runner.

```
bolt-gps-copilot/
  index.html          UI only: state rendering, map, dashboard, ride controls,
                      paired Monte-Carlo panel, live-data entry/export.
  engine.js           Pure, dependency-free economic core (also loads from Node).
  docs/HIGHLANDER-VALIDATION-DESIGN.md   (this file)
  audit/              unchanged audit artifacts + new experiment runner that
                      requires engine.js (Node) for CI-scale runs.
  export.json/.csv    generated by live-data export / import.
```

- `engine.js` exposes: `ECON` (config), fare model, fuel model, time/ledger accounting, demand model (zones/OD/bands), Copilot policy, Baseline policy, `simShift(mode, seed)`, `simPaired(seed, n)`, invariant checker, target-discovery statistics.
- `index.html` wires the UI to `engine.js`; all DOM updates stay there. One `<script src="engine.js">` before the UI script (`file://`-safe, no modules, Node-compatible). If the app grows, `engine.js` can be split later without UI change.
- `audit/experiment.js` (Node): runs the required paired baseline-vs-Copilot Monte Carlo at CI scale and writes `results-second-order-phase2.txt` plus a short report inline. Uses the **same `ECON`/engine.js** — no duplicated math.

**No teleports, no forced trips, no hidden commission, no time-distortion.** The core is a minute-accounted discrete-event shift; the Copilot produces advisory decisions; only the driver (or the sim) moves the vehicle — physically, at speed, costing fuel and time.

## B. Economics ledger

Canonical, always-visible identity (invariant enforced by tests):

```
NET_AFTER_FUEL ≡ RIDER_GROSS_FARES − BOLT_COMMISSION − PETROL_COST
```

Explicit line items — every shift produces one **ShiftLedger**:

| row | definition |
|---|---|
| RIDER_GROSS_FARES | Σ per-trip fare charged to rider (distance/time model × surge) |
| BOLT_COMMISSION | 20% of RIDER_GROSS (round one decimal, driver-side deduction) |
| DRIVER_REVENUE_AFTER_COMMISSION | RIDER_GROSS − BOLT_COMMISSION |
| TOTAL_LITRES | LITRES_DRIVING + LITRES_IDLE |
| LITRES_DRIVING | TOTAL_KM / 100 × L/100km × AC |
| LITRES_IDLE | IDLE_H × ENGINE_ON_FRAC × IDLE_L/H |
| PETROL_COST | TOTAL_LITRES × PRICE |
| **NET_AFTER_FUEL** | after-commission revenue − PETROL_COST |

**KM ledger** (separate, auditable): `PAID_KM, PICKUP_KM, RELOCATION_KM, OTHER_UNPAID_KM, TOTAL_KM = PAID+PICKUP+RELOC+OTHER`. UNPAID_KM = TOTAL − PAID.

**TIME ledger:** `PICKUP_MIN, RIDE_MIN, DWELL_MIN, IDLE_MIN, RELOCATION_MIN` with the invariant `PICKUP+RIDE+DWELL+IDLE+RELOCATION = SHIFT_MINUTES` (±1 min tolerance).

**Labeling rule:** NET_AFTER_FUEL is **never labeled profit**. Maintenance, depreciation, repairs, insurance, financing, tyres are **excluded** from every pass/fail and labeled "DEFERRED (post-fuel validation)". Every projection is explicitly tagged `SIMPLE PACE ESTIMATE` or `ESTIMATED MONTH-END (basis: actual MTD)`.

## C. Copilot decision algorithm

**Primary objective:** maximize expected `NET_AFTER_FUEL / remaining minute` (equivalently maximize expected NET_AFTER_FUEL for the rest of the finite shift).

Zone evaluation — for candidate zone `z` and current time `t`:

```
d          = distance(driver.loc, z.centroid)
t_reloc    = d / RELOCATION_SPEED            # physical move, costs TIME
fuel_reloc = d × (L/100km × AC) / 100
rate       = hourlyDemand(z, hour) × captureProb(hour)          # offers per h
E_cycle    = expectedPickupMin  + expectedRideMin + DWELL_MIN
E_fare     = fareCard(paidKm_expected, rideMin_expected) × surge(hour,dow,rain,event)
E_pickupKm = expectedPickupDistance(z, hour)
E_netCycle = E_fare×(1−COMM) − fuel(paidKm+E_pickupKm, cycleTime) − idleFuel(cycleTime)
E_netHr(z) = min(rate, MAX_TRIPS_PER_HOUR) × E_netCycle − idleFuelForUnfilledHour
STAY_VALUE  = E_netHr(currentZone) × REMAINING_MIN
RELOC_VALUE(z) = E_netHr(z) × (REMAINING_MIN − t_reloc) − fuelCost(fuel_reloc) − RISK_PREMIUM
```

Decision (per recommendation tick, ~ every 30 min and after every trip):
1. `z* = argmax RELOC_VALUE(z)` over all zones.
2. Recommend **RELOCATE z\*** only if `RELOC_VALUE(z*) > STAY_VALUE + RISK_PREMIUM` (§6). Otherwise **STAY / WAIT / ACCEPT**.
3. Trip-level gate for each incoming offer: accept only if trip `E_netCycle > 0` AND pickup distance ≤ ACCEPT_RADIUS.

**Conserve / stop modes (§7)** — triggers evaluated each tick:
- trailing rolling `NET_AFTER_FUEL` (last 3 h) < 0 and expected next-hour EV negative → **CONSERVE** (stay put, engine-off waits, reject low-quality offers).
- demand band extremely low and `E_netHr(any zone) < END_SHIFT_THRESHOLD` → **END SHIFT** (advised, not forced).
- fuel < 15 L → **CONSERVE**; fuel < 8 L → **END SHIFT**.
- excessive expected pickup (> 5 km) → **DECLINE + WAIT**.

Message vocabulary: `ACCEPT, DECLINE, STAY, WAIT, REPOSITION, CONSERVE, END SHIFT`. Every recommendation carries its expected `NET_AFTER_FUEL/hour` so the cost of each action is explicit (no teleports; relocation always deducts time+fuel+km).

Honesty rule (§17): inputs tagged `OBSERVED` (GPS, entered rides) / `ESTIMATED` (hourly demand bands) / `INFERRED` (surge inference from accept/reject history). The system never claims Bolt-internal demand/surge data.

**Proposed defaults** (all in `ECON`, tunable; rationale → treat as priors, re-tuned against the §7 reconciliation run before any Copilot credit is claimed):

| parameter | proposed default | rationale |
|---|---|---|
| `ACCEPT_RADIUS` | 3.0 km | matches corrected-model `accept`, keeps Copilot/baseline trip-quality comparable |
| `MAX_TRIPS_PER_HOUR` | 3 | matches second-order `tripThisHour < 3` cap |
| `RELOCATION_SPEED` | 20 km/h | Abuja in-city average (cross-check vs `CLASS_SPEED` ff/pk midpoints) |
| `RISK_PREMIUM` | ₦500 flat per relocation decision (config 0–₦2,000) | covers demand-estimate error + reposition downside; prevents over-rotation in low demand |
| `END_SHIFT_THRESHOLD` | `max(E_netHr over zones) < ₦500/h` | advises (never forces) end-of-shift on structurally negative hours |
| `CONSERVE_FUEL` | 15 L → CONSERVE; 8 L → END SHIFT | reserve so the driver reaches the pump |
| `TRAILING_WINDOW` | 3 h rolling NET_AFTER_FUEL < 0 | §7 conserve trigger |

These are defaults, not conclusions; §22 tunes them against the reconciliation run and documents any drift.

## D. Baseline driver behavior

A **reasonable human**, not a strawman. The baseline is defined **identically to the corrected-model (second-order `daySim`) default behavior**, so the reconciliation invariant in §7 is exact — the baseline *is* the audited model with its defaults, and its ~₦0/day (card B, V6, AC 1.04) reproduction is the sanity anchor. Fixed, documented policy (all constants from `ECON` / `second-order.js def()`):

1. **Acceptance:** pickup ≤ **3.0 km** (`accept`) or decline; 6% rider-cancel rate (`cancelP`).
2. **Relocation:** when idle > 15 min, reposition with probability **0.65** (`relocProb`) toward a top-3 weighted zone, capped at **2.6 km** (`relocKm`) partial travel — no zone-arbitrage, no surge-timing, no rolling-NET gating. This is exactly what the Copilot is allowed to improve on.
3. **Waiting/dwell:** engine-on idle fraction **0.50** → wait-idle fuel **0.75 L/h** (`1.5 × 0.5`); dwell on-site **1.2 m** + post-trip **1.6 m**; pickup prep **+1.5 m**.
4. **Shift:** fixed **12 h** from configurable start (`shiftStart` 6.5), or end early at fuel < 8 L.
5. No predictive zone arbitrage, no surge-timing, no rolling-NET gating — that is precisely what differentiates copilot.

IMPLEMENTATION: `engine.baselineShift(seed)` reuses the *same* movement/fuel/fare primitives as `engine.simShift`, but its decision layer is a **fixed script** (the rules above). Deterministic given seed; no Copilot subroutines consumed. Differences vs Copilot are **solely** the decision strategy (§11).

Baseline − vs Copilot − **only** difference = decision strategy.

Keep current layout, replace semantics. Left card (ledger-first):
- RIDER_GROSS / BOLT_COMMISSION / AFTER-COMMISSION REVENUE / PETROL_COST / **NET_AFTER_FUEL** (big, green/red).
- Rows: `NET/h`, `NET/km`, `FUEL ₦/km`, `AFTER-COMM ₦/km`, `FUEL USED (L)`, `TOTAL KM`, `UNPAID KM`, `TRIPS`, `IDLE TIME`, mode badge `BASELINE | COPILOT`.

Reference target block (§8, §9) — each metric carries an explicit, honest tag:
- `REFERENCE TARGET ₦300,000/mo (₦11,538.46/day line)` — always visible, never celebratory, non-decisional.
- `ACTUAL MONTH-TO-DATE NET_AFTER_FUEL` (from stored daily ledgers; = ₦0 until live days exist). The only number that ever triggers "target reached".
- `ESTIMATED DAILY NET_AFTER_FUEL` = current-shift completed NET (or last-completed-day NET while pre-shift) — labeled *estimate*, distinct from actual.
- `SIMPLE PACE ESTIMATE` = last-completed-shift NET × 26 — **explicitly labeled as a pace estimate, never used as evidence**.
- `PROJECTED 26-DAY NET_AFTER_FUEL` = ACTUAL MTD + (last-shift NET × remaining days) — labeled *projection*, not a measurement.
- "Target reached" is shown only when **ACTUAL MTD ≥ ₦300,000**; never on a single good day (§9, §20).

Target-discovery card (§10, §15): once ≥ 21 daily shifts logged, render the monthly NET_AFTER_FUEL distribution — `P25 / P50 / P75 / P90`, plus average / median / best / worst month — and derive the **three-case forecast**:
- `LOW CASE`  = P25 daily NET × 26
- `BASE CASE` = P50 daily NET × 26
- `HIGH CASE` = P75 daily NET × 26
- **Forecast interval** = [P25, P75] of projected month (labelled as a distribution band, not a guarantee). The live 26-day result is judged on whether actual MTD lands *within* this interval, not against ₦300k (§15).

Headline stays: "What can this vehicle consistently achieve?" — never "how to make ₦300k".

Copilot value card (§14): `INCREMENTAL NET_AFTER_FUEL/shift` (paired mean), `/month`, `fuel L saved/shift`, `unpaid km reduced/shift`, `idle h reduced/shift`, `trip-quality delta` — causally explanatory only; the KPI is the paired NET difference (§12).

Chart: 12-ride gross → 12-trip NET_AFTER_FUEL bars. Map/rankings unchanged in spirit but scores replaced by `E_netHr` (est. ₦/h), not boost.

## G. Simulation changes (`engine.js` core)

1. **Minute time accounting:** shift = SHIFT_MIN (default 720). Loop minute-by-minute (or event steps with time deltas); pickup/ride/dwell/idle/relocation all consume time. **No "1 ride = 1 hour."**
2. **Demand model** (from second-order BAND/OD): hourly offers = `baseHourlyRate × band[hour] × capture × demandMult`, Poisson-thinned; origins drawn from the 72% local / radial-decay mix; destinations from zone/OD classes with airport share 4.5% — **airport trips arise probabilistically, never forced** (§4).
3. **Physical movement:** relocation is `km at avg speed` → time + fuel; copilot/baseline decisions never teleport.
4. **Fare model** (§1): `fare = max(card.min, card.start + card.perKm×paidKm + card.perMin×rideMin) × surge(hour, dow, rain, event)`. Commission deducted explicitly.
5. **Fuel model** (§2): LT—config `l100`, `acFactor`, `idleLPerHr`, `engineOnFrac`; separate `PAID/PICKUP/RELOCATION/OTHER` km; litres & cost tallied per §B. Vehicle configurable per §6 of the directive (Copilot is vehicle-agnostic).
6. **Shift end:** fuel reserve or end-of-shift or copilot END SHIFT advice (not forced).
7. Ledger + invariant per shift: assert `NET_AFTER_FUEL = gross − commission − petrol` within ₦0.05; assert time ledger = SHIFT_MIN.

## H. Paired baseline-vs-Copilot experiment design

- **Pairing method: Common Random Numbers (CRN), adopted (§13/§H).** True identical offer streams are unrealizable here — a Copilot relocation changes driver location, hence origin draws, hence the demand that arrives. The clean, standard solution is CRN: share the random seed for all **exogenous** shocks ($dow$, rain, event, surge draws, OD/traffic stochasticity, cancel draws), and let **location-dependent** offers diverge by strategy. This controls confounding weather/surge/day variance while still crediting only strategy differences.
- `simPaired(seed, N)`: for i in 1..N: draw `env_i` (exogenous stream) from `seed_i`; run Baseline and Copilot through the **same `env_i`**; record both ledgers.
- Outputs: mean & 95% CI and full distribution of `ΔNET = COPILOT_NET − BASELINE_NET` per shift; month-equivalent Δ (×26); secondary deltas (fuel L, unpaid km, idle h, net/h, net/fare) **for explanation only** — never summed as additive benefits (§12).
- Tests: paired t + bootstrap CI + sign test; report `incremental ≥ 0` proportion; even report "Copilot not yet measurably better" if CI includes 0 (truth-seeking).
- Sizes: browser panel default 1,000 paired shifts (~1–3 s); Node harness up to 10,000 for the audit artifact. Seeds reproducible (`mulberry32`).
- Also run per-vehicle sensitivity (l100 14/12.5/10/7/6/5) to answer "does Copilot's value scale with vehicle efficiency".

## M. Success criteria (directive §23)

The project is successful only if it answers these six questions honestly — none of them reference ₦300k as a target to hit:

1. **What can this 2005 Highlander realistically earn after fuel on Bolt in Abuja?** → answered by the simulated base-case daily NET_AFTER_FUEL distribution + its reconciliation to `results-second-order.txt`.
2. **What is the Highlander's sustainable monthly NET_AFTER_FUEL range?** → answered by the three-case forecast interval (P25–P75, plus P90/best/worst) once ≥ 21 days of data exist.
3. **How much additional NET_AFTER_FUEL does the Copilot actually create?** → answered by the paired baseline-vs-Copilot ΔNET (mean + 95% CI), never by summing channel ceilings.
4. **What mechanisms create that improvement?** → answered only as *explanatory* component deltas (fuel L, unpaid km, idle h, trip quality); the causal claim rides on the paired design.
5. **Can the Copilot make a meaningful economic difference even if the vehicle cannot reach ₦300k?** → answered by whether ΔNET/shift is positive and material at the Highlander's efficiency, independent of the ₦300k benchmark.
6. **What does the one-month live test need to measure to distinguish simulation error from real-world performance?** → answered by the §I schema (per-ride + per-shift ledger, copilot-adherence flag) and the forecast-interval check in §15.

**Guiding constraint (repeated for the record):** do not optimize the software to produce ₦300k. Optimize the experiment to discover the truth. The Highlander is the validation vehicle because it is the vehicle actually available; ₦300k is the original benchmark, not the answer being manufactured.
